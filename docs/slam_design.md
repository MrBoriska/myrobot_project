# myrobot_custom_slam — дизайн и Numbers

Документ описывает SLAM-пакет `src/myrobot_custom_slam`: зачем он переписан,
как устроен алгоритм, какие компромиссы выбраны под Orange Pi Zero 3 (Allwinner
H618, 4×Cortex-A53 @ 1.5 ГГц, Mali-G31 MP2, LPDDR4) и какие измерения это
подтверждают.

## 1. Что было в исходной ветке Jules и что исправлено

| Было | Стало |
|---|---|
`kernels/scan_matching.cl`: brute-force поиск ближайшего соседа по всему
`map[]` на GPU (`O(N_scan × N_map)`) | 2D-хэш-сетка 0.1 м + подгонка линии по
3×3 (при нехватке точек 5×5) соседям: `O(1)` на точку, без ядра OpenCL |
Утечка OpenCL-буферов на каждый скан, `clCreateBuffer` в аргументе
`clEnqueueMapBuffer`, чтение через `CL_MEM_USE_HOST_PTR` без map/unmap | OpenCL
убран полностью — на Mali-G31 он memory-bound и проигрывает L2-резидентной
хэш-сетке (см. §6) |
Неинициализированные `cl_kernel_`/`cl_prog_` и `clRelease*` по мусору в
деструкторе | RAII-классы без OpenCL-хендлов вообще |
`map -> odom` публиковался как полная поза робота (ветка «corrected TF tree» на
самом деле ломала TF: база оказывалась на удвоенной позе) | `map -> odom`
считается как поправка `T_map_base · T_odom_base⁻¹` по TF; при отсутствии
`odom -> base_link` публикуется `map -> base_link` с предупреждением |
Нет публикации карты | `nav_msgs/OccupancyGrid` на `/map` (QoS transient_local,
0.5 Гц) + `sensor_msgs/PointCloud2` зарегистрированного скана |
`launch/slam_gazebo.launch.py` запускал только сам узел | полноценный bring-up:
Gazebo + `robot_state_publisher` + `spawn_entity` + SLAM + RViz |
Тест `test/test_slam.cpp` не подключён в CMake, «тест» печатал состояние |
19 gtest-кейсов: сетка/линия, инициализация и численная устойчивость ESKF,
регистрация в синтетической комнате, ограниченность карты, плюс benchmark |
`package.xml` без OpenCL/Eigen зависимостей | зависимости объявлены, OpenCL не
нужен вовсе |
Плоскостная задача решалась как 3D (z/roll/pitch дрейфуют, они ненаблюдаемы
одноплоскостным лидаром) | опциональная проекция на SE(2) (`planar: true`) с
обнулением ненаблюдаемых компонент ковариации |
`timer = 1000ms / gyro_range` (делил на диапазон гироскопа!) в
`ros2_mpu9250_driver` | не трогали — вне области задачи, отмечено ниже как
известный дефект |

│   ├── eskf.cpp

Ядро (`voxel_map`, `eskf`) не зависит от ROS — поэтому его можно тестировать и
бенчмаркать без `roscore`/DDS.

## 3. Алгоритм

Формулировка — FAST-LIO2, адаптированная к одноплоскостному 2D-лидару.

**Номинальное состояние** `x = {q, p, v, ba, bg, g}` (`q`: body→world).

**Ошибка** — 18 DoF: `dp, dθ, dv, dba, dbg, dg`. Порядок фиксирован в
`common.hpp` (`enum ErrIdx`).

**Predict** (на каждом IMU-сэмпле, 100 Гц):

```
a = acc - ba;  ω = gyro - bg
p ← p + v·dt + ½(R·a + g)·dt²
v ← v + (R·a + g)·dt
q ← q ⊗ Exp(ω·dt)
F = I + A·dt  (A: ∂p/∂v=I, ∂θ/∂θ=-[ω]×, ∂v/∂θ=-R[a]×, ∂v/∂ba=-R, ∂v/∂g=I)
P ← F·P·Fᵀ + Q
```

`dt` ограничен 50 мс — чтобы потерянный пакет не выбросил состояние.

**Update** — итеративный Гаусс-Ньютон по сырому скану (без выделения признаков):

* для каждой точки: `p_imu = R_lidar_imu · p_lidar + t_lidar_imu`,
  `p_w = R·p_imu + p`;
* соответствие — ближайшая **линия**, подогнанная по точкам карты в 3×3 (при
  нехватке — 5×5) ячейках: 2×2 ковариация → собственные числа в замкнутой форме;
  линия валидна, если `λ_min < 0.20·λ_max` и `λ_max > 1e-4 м²`;
* остаток `r = nᵀp_w − d` (знаковое расстояние до линии);
* якобиан только по `(dp, dθ)`:
  `∂r/∂dp = n`, `∂r/∂dθ = −(Rᵀn) × p_imu` — блок 6×6 вместо 18×18 (в 9 раз
  меньше FLOP на точку);
* отбраковка: `|r| > max_residual` (0.25 м) — жёсткий гейт; внутри гейта —
  Huber-вес с коленом `huber_delta` (0.06 м);
* итерация (формула FAST-LIO2, именно она обеспечивает сходимость):

  ```
  A_j      = HᵀWH + P⁻¹
  δ_{j+1}  = A_j⁻¹ (HᵀW r_j + HᵀWH·δ_j)
  x̂_{j+1}  = x_lin ⊞ δ_{j+1}
  ```

  (без слагаемого `HᵀWH·δ_j` итерация «прыгает» между prior'ом и решением —
  ровно эта ошибка была в первой версии, см. §5);
* остановка при `‖δ_{j+1} − δ_j‖ < converge_eps` (1 мм) или 4 итерациях;
* ковариация после сходимости — в информационной форме, `P⁺ = A⁻¹`, с полом
  на позе (`pose_cov_floor_*`): ошибки точек вдоль одной стены коррелированы,
  и «независимая» модель шума делает фильтр самоуверенным и вялым на реальных
  данных.

**Deskew (motion compensation).** `predict` уже ведёт историю поз (2 с), поэтому
для точки со временем `t₀ + i·time_increment` берётся интерполированная поза
(lerp по `p`, slerp по `q`) и точка переносится в систему начала скана:
`p_lidar(t₀) = T_il⁻¹ · T(t₀)⁻¹ · T(t)`.

**Карта.** Хэш-сетка 0.1 м, до 12 точек на ячейку (кольцевая перезапись),
дедупликация 2 см, жёсткий потолок `voxel_max_cells` (40000 ячеек ≈ 7 МБ).
Вставка — только по inlier'ам последней итерации. Никаких аллокаций после
прогрева: ячейки POD, `unordered_map` с `reserve`.

**Публикации.** `map -> odom` (коррекция), `/map` (OccupancyGrid), 
`/slam/registered_scan` (PointCloud2 в `map`), плюс throttle-логи со временем
скана, числом итераций, inlier'ов, RMS и размером карты.

## 4. Почему `/imu/data_raw`

`imu_filter_madgwick` в `description.launch.py` публикует фильтрованную
ориентацию на `/imu`, но для распространения состояния нужны сырые accel/gyro
(ориентация Madgwick — уже продукт другого фильтра, использовать её как вход
ESKF нельзя без двойного счёта). Поэтому по умолчанию `imu_topic:
/imu/data_raw` (выход `mpu9250driver`). В Gazebo `gazebo_ros_imu_sensor`
ремапится в тот же `/imu/data_raw`, так что `slam.yaml` одинаков для железа и
симуляции.

## 5. Дефекты, найденные и исправленные по ходу

Помимо пунктов из §1, в самом алгоритме на первом прогоне были две настоящие
ошибки, обе пойманы тестами и измерены:

1. **Знак гаусс-ньютоновского шага.** Остаток определён как `r = h(x) − z`,
   поэтому шаг — `δ = −A⁻¹HᵀWr`, а не `+`. С неверным знаком фильтр уезжал от
   решения (поза `x = −0.128` при истине `+0.12`).
2. **Отсутствие переноса prior'а в итерации.** Без `HᵀWH·δ_j` итерация
   осциллировала: чётные итерации уходили к решению, нечётные — назад к prior'у,
   решение не получалось ни за 4, ни за 6 итераций (`x = 0.019` вместо `0.12`).

После исправления — сходимость за 2–3 итерации до миллиметрового RMS.

## 6. Измерения

`bench_slam` (синтетическая комната 18×18 м, робот едет по окружности R=5 м,
карта растёт):

| скан | сканов | принято | среднее | худшее | RMS | итераций | карта |
|---|---|---|---|---|---|---|---|
720 точек | 300 | 300 | **0.237 мс** | 0.60 мс | 1.5 мм | 2.0 | 2885 pts / 907 cells |
360 точек | 300 | 299 | **0.163 мс** | 0.27 мс | 2.0 мм | 2.3 | 2239 pts / 692 cells |
720 точек | 600 | 600 | **0.294 мс** | 0.84 мс | 4.2 мм | 2.3 | 4862 pts / 1148 cells |

Это x86-64 (`-O3 -march=native`). Для A53 разумный коэффициент 3–6× → **1–2 мс
на скан**, то есть ~2 % бюджета 10 Гц лидара. Расход памяти: карта ограничена
`voxel_max_cells × sizeof(Cell)` = 40000 × 176 Б ≈ 7 МБ, стек/хип на скан — ноль
после прогрева.

Отсюда и решение не тащить OpenCL: на Mali-G31 поиск соседей упирается в
пропускную способность LPDDR4 (общая с CPU), а не в арифметику; brute-force по
всему облаку карты — это ещё и `O(N_scan × N_map)`, что на 4862 точках карты и
720 точках скана даёт 3.5 млн сравнений на скан против ~9 хэш-проб на точку в
сетке.

## 7. Тюнинг под Orange Pi Zero 3

* CPU governor на `performance` (`cpufrequtils`) либо `ondemand` с
  `up_threshold` ~40 — фильтр даёт редкие всплески, а не постоянную нагрузку.
* Драйвер колёс (`myrobot_driver`) и SLAM не конкурируют за ядро: у первого
  10 мс-таймер, у второго — событийный callback. При желании:
  `taskset -c 2 ros2 run ...` + `chrt -f 20`.
* `myrobot_wheel_fb` блокируется в `poll()` на sysfs — почти нулевой CPU, но
  при 1.6 кГц импульсов два узла дают заметный wakeup-rate; при проблемах с
  джиттером уменьшить частоту прерываний нельзя (аппаратно), зато можно
  поднять приоритет: `nice -n -18` (закомментировано в `description.launch.py`).
* Карта на 40×40 м при 0.05 м — 640k клеток OccupancyGrid (≈1.3 МБ на
  публикацию); при нехватке памяти уменьшить `map_max_extent`.
* `/dev/ttyS5` для лидара должен быть `chmod 0666` (см. `setup_gpio.sh`);
  UART5 на H618 не должен использоваться консолью.

## 8. Как запускать

```bash
# реальный робот: драйверы + описание + SLAM
ros2 launch myrobot_custom_slam slam.launch.py use_rviz:=true

# симуляция
ros2 launch myrobot_custom_slam slam_gazebo.launch.py

# только узел (если стек уже поднят)
ros2 run myrobot_custom_slam slam_node --ros-args \
  --params-file $(ros2 pkg prefix myrobot_custom_slam)/share/myrobot_custom_slam/config/slam.yaml

# бенчмарк ядра
ros2 run myrobot_custom_slam bench_slam 720 300

# тесты
colcon test --packages-select myrobot_custom_slam
```

Первые ~1 с после старта — инициализация IMU (100 статических сэмплов): узел
оценивает смещения гироскопа/акселерометра и выравнивает платформу по вектору
гравитации. Робот в этот момент должен стоять; при движении инициализация
повторяется.

## 9. Ограничения и следующие шаги

* **Нет loop closure.** Это LIO, как и FAST-LIO2: дрейф по курсу накапливается
  (типично 0.5–2 % пути для 2D-лидара с IMU). Следующий шаг — позовый граф с
  ключевыми кадрами и поиском петель по дескрипторам скан-контекста
  (Scan Context / M2DP), затем глобальная оптимизация g2o/GTSAM.
* **Нет сохранения/загрузки карты.** Для повторной локализации нужен
  `serialize()/deserialize()` у `VoxelMap` + `map_server`-совместимый формат.
* **IMU-инициализация требует покоя.** Для «холодного» старта на ходу нужен
  статический детектор по скользящему окну (дисперсия акселерометра).
* **`ros2_mpu9250_driver`**: `frequency` в `mpu9250driver.cpp` считается как
  `1000ms / gyro_range`, то есть при `gyro_range: 0` узел делит на ноль/получает
  0 и частота публикации не та, что задана параметром `frequency`. Не правили,
  чтобы не менять поведение чужого пакета в этой ветке — при переходе на сырой
  IMU стоит исправить (`1000ms / frequency`).
