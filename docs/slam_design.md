# myrobot_custom_slam — дизайн и Numbers

Документ описывает SLAM-пакет `src/myrobot_custom_slam`: зачем он переписан,
как устроен алгоритм, какие компромиссы выбраны под Orange Pi Zero 3 (Allwinner
H618, 4×Cortex-A53 @ 1.5 ГГц, Mali-G31 MP2, LPDDR4) и какие измерения это
подтверждают.

## 1. Что было в исходной ветке Jules и что исправлено

| Было | Стало |
|---|---|
`kernels/scan_matching.cl`: brute-force поиск ближайшего соседа по всему
`map[]` на GPU (`O(N_scan × N_map)`) | 2D-хэш-сетка 0.1 м + подгонка линии по
3×3 (при нехватке точек 5×5) соседям: `O(1)` на точку, без ядра OpenCL |
Утечка OpenCL-буферов на каждый скан, `clCreateBuffer` в аргументе
`clEnqueueMapBuffer`, чтение через `CL_MEM_USE_HOST_PTR` без map/unmap | OpenCL
убран полностью — на Mali-G31 он memory-bound и проигрывает L2-резидентной
хэш-сетке (см. §6) |
Неинициализированные `cl_kernel_`/`cl_prog_` и `clRelease*` по мусору в
деструкторе | RAII-классы без OpenCL-хендлов вообще |
`map -> odom` публиковался как полная поза робота (ветка «corrected TF tree» на
самом деле ломала TF: база оказывалась на удвоенной позе) | `map -> odom`
считается как поправка `T_map_base · T_odom_base⁻¹` по TF; при отсутствии
`odom -> base_link` публикуется `map -> base_link` с предупреждением |
Нет публикации карты | `nav_msgs/OccupancyGrid` на `/map` (QoS transient_local,
0.5 Гц) + `sensor_msgs/PointCloud2` зарегистрированного скана |
`launch/slam_gazebo.launch.py` запускал только сам узел | полноценный bring-up:
Gazebo + `robot_state_publisher` + `spawn_entity` + SLAM + RViz |
Тест `test/test_slam.cpp` не подключён в CMake, «тест» печатал состояние |
19 gtest-кейсов: сетка/линия, инициализация и численная устойчивость ESKF,
регистрация в синтетической комнате, ограниченность карты, плюс benchmark |
`package.xml` без OpenCL/Eigen зависимостей | зависимости объявлены, OpenCL не
нужен вовсе |
Плоскостная задача решалась как 3D (z/roll/pitch дрейфуют, они ненаблюдаемы
одноплоскостным лидаром) | опциональная проекция на SE(2) (`planar: true`) с
обнулением ненаблюдаемых компонент ковариации |
`timer = 1000ms / gyro_range` (делил на диапазон гироскопа!) в
`ros2_mpu9250_driver` | не трогали — вне области задачи, отмечено ниже как
известный дефект |

## 3. Алгоритм

Формулировка — FAST-LIO2, адаптированная к одноплоскостному 2D-лидару.

**Номинальное состояние** `x = {q, p, v, ba, bg, g}` (`q`: body→world).

**Ошибка** — 18 DoF: `dp, dθ, dv, dba, dbg, dg`. Порядок фиксирован в
`common.hpp` (`enum ErrIdx`).

**Predict** (на каждом IMU-сэмпле, 100 Гц):

```
a = acc - ba;  ω = gyro - bg
p ← p + v·dt + ½(R·a + g)·dt²
v ← v + (R·a + g)·dt
q ← q ⊗ Exp(ω·dt)
F = I + A·dt  (A: ∂p/∂v=I, ∂θ/∂θ=-[ω]×, ∂v/∂θ=-R[a]×, ∂v/∂ba=-R, ∂v/∂g=I)
P ← F·P·Fᵀ + Q
```

`dt` ограничен 50 мс — чтобы потерянный пакет не выбросил состояние.

**Update** — итеративный Гаусс-Ньютон по сырому скану (без выделения признаков):

* для каждой точки: `p_imu = R_lidar_imu · p_lidar + t_lidar_imu`,
  `p_w = R·p_imu + p`;
* соответствие — ближайшая **линия**, подогнанная по точкам карты в 3×3 (при
  нехватке — 5×5) ячейках: 2×2 ковариация → собственные числа в замкнутой форме;
  линия валидна, если `λ_min < 0.20·λ_max` и `λ_max > 1e-4 м²`;
* остаток `r = nᵀp_w − d` (знаковое расстояние до линии);
* якобиан только по `(dp, dθ)`:
  `∂r/∂dp = n`, `∂r/∂dθ = −(Rᵀn) × p_imu` — блок 6×6 вместо 18×18 (в 9 раз
  меньше FLOP на точку);
* отбраковка: `|r| > max_residual` (0.25 м) — жёсткий гейт; внутри гейта —
  Huber-вес с коленом `huber_delta` (0.06 м);
* итерация (формула FAST-LIO2, именно она обеспечивает сходимость):

  ```
  A_j      = HᵀWH + P⁻¹
  δ_{j+1}  = A_j⁻¹ (HᵀW r_j + HᵀWH·δ_j)
  x̂_{j+1}  = x_lin ⊞ δ_{j+1}
  ```

  (без слагаемого `HᵀWH·δ_j` итерация «прыгает» между prior'ом и решением —
  ровно эта ошибка была в первой версии, см. §5);
* остановка при `‖δ_{j+1} − δ_j‖ < converge_eps` (1 мм) или 4 итерациях;
* ковариация после сходимости — в информационной форме, `P⁺ = A⁻¹`, с полом
  на позе (`pose_cov_floor_*`): ошибки точек вдоль одной стены коррелированы,
  и «независимая» модель шума делает фильтр самоуверенным и вялым на реальных
  данных.

**Deskew (motion compensation).** `predict` уже ведёт историю поз (2 с), поэтому
для точки со временем `t₀ + i·time_increment` берётся интерполированная поза
(lerp по `p`, slerp по `q`) и точка переносится в систему начала скана:
`p_lidar(t₀) = T_il⁻¹ · T(t₀)⁻¹ · T(t)`.

**Карта.** Хэш-сетка 0.1 м, до 12 точек на ячейку (кольцевая перезапись),
дедупликация 2 см, жёсткий потолок `voxel_max_cells` (40000 ячеек ≈ 7 МБ).
Вставка — только по inlier'ам последней итерации. Никаких аллокаций после
прогрева: ячейки POD, `unordered_map` с `reserve`.

**Публикации.** `map -> odom` (коррекция), `/map` (OccupancyGrid), 
`/slam/registered_scan` (PointCloud2 в `map`), плюс throttle-логи со временем
скана, числом итераций, inlier'ов, RMS и размером карты.

## 4. Почему `/imu/data_raw`

`imu_filter_madgwick` в `description.launch.py` публикует фильтрованную
ориентацию на `/imu`, но для распространения состояния нужны сырые accel/gyro
(ориентация Madgwick — уже продукт другого фильтра, использовать её как вход
ESKF нельзя без двойного счёта). Поэтому по умолчанию `imu_topic:
/imu/data_raw` (выход `mpu9250driver`). В Gazebo `gazebo_ros_imu_sensor`
ремапится в тот же `/imu/data_raw`, так что `slam.yaml` одинаков для железа и
симуляции.

## 5. Дефекты, найденные и исправленные по ходу

Помимо пунктов из §1, в самом алгоритме на первом прогоне были две настоящие
ошибки, обе пойманы тестами и измерены:

1. **Знак гаусс-ньютоновского шага.** Остаток определён как `r = h(x) − z`,
   поэтому шаг — `δ = −A⁻¹HᵀWr`, а не `+`. С неверным знаком фильтр уезжал от
   решения (поза `x = −0.128` при истине `+0.12`).
2. **Отсутствие переноса prior'а в итерации.** Без `HᵀWH·δ_j` итерация
   осциллировала: чётные итерации уходили к решению, нечётные — назад к prior'у,
   решение не получалось ни за 4, ни за 6 итераций (`x = 0.019` вместо `0.12`).

После исправления — сходимость за 2–3 итерации до миллиметрового RMS.

## 6. Измерения

### 6.1 Точность (закрытый контур, синтетика)

`fake_sensors` + `check_slam_accuracy`, круг R=1 м, скорость 0.3 м/с,
720 лучей, 100 Гц IMU, ошибка масштаба одометрии 2 %, смещение гироскопа
0.002 рад/с. Ошибка — между TF `map -> base_link` и истинной позой:

| сценарий | средняя | худшая | финальная | курс (сред/худ) | итог |
|---|---|---|---|---|---|
штатный, **170 с / 51 м** (~8 кругов) | **0.64 см** | 2.20 см | 0.63 см | 0.14° / 1.50° | PASS |
ошибка одометрии **10 %** (вместо 2 %) | 0.75 см | 2.84 см | 0.84 см | 0.16° / 1.48° | PASS |
скорость **1.0 м/с**, R=1.5 м | 2.11 см | 9.85 см | 1.78 см | 0.61° / 3.35° | PASS |
робот стоит 25 с | 0.26 см | 0.42 см | 0.31 см | 0.02° / 0.05° | PASS |
шум лидара **3 см** (в 3× хуже паспорта) | 6.08 см | 14.89 см | 7.47 см | 0.37° / 1.07° | PASS |
шум 3 см **+ 10 % выпадений** | 5.95 см | 13.53 см | 8.48 см | 0.16° / 0.52° | PASS* |

\* со 9 отброшенными сканами и 3 перезапусками карты (см. §9.9): при таком шуме
захват периодически теряется, и без восстановления ошибка была бы 38 см средняя /
176 см худшая (измерено), а дальше — потеря навсегда.

Что это значит: дрейфа как такового нет — за 51 м и 8 кругов ошибка не растёт
(0.63 см в конце против 0.64 см в среднем), потому что `map -> odom` непрерывно
съедает ошибку колёсной одометрии (в т.ч. 10 %). Ошибка — это шум измерения
плюс систематика экструзивов, а не накопление. Курс держится 0.14° средняя.

### 6.2 Производительность

`bench_slam` (синтетика, x86-64, `-O3 -march=native`, один поток):

| скан | сканов | среднее | худшее | RMS | итераций | карта |
|---|---|---|---|---|---|---|
360 точек | 400 | **0.135 мс** | 0.34 мс | 2.5 мм | 2.3 | 2851 pts / 828 cells |
720 точек | 400 | **0.216 мс** | 0.62 мс | 2.7 мм | 2.1 | 3959 pts / 1042 cells |
720 точек | 1500 | **0.291 мс** | 0.66 мс | 5.7 мм | 2.4 | 9345 pts / 1964 cells |

Узел целиком на 10 Гц лидара: **3.4–4.4 % одного ядра**, RSS **25 МБ**
(из них карта ограничена `voxel_max_cells × 176 Б` ≈ 7 МБ), задержка на скан
**0.3–2.5 мс** (`scan ... ms` в логе — включая публикации и TF).

С поправкой 3–6× для Cortex-A53 это 0.4–1.7 мс на скан, то есть 0.5–2 %
бюджета 10 Гц. Узкое место на Orange Pi — не фильтр, а DDS/TF и публикация
`/map` (640k клеток при `map_max_extent: 40`; теперь окно считается по данным,
для комнаты 8×8 м это 202×202 = 41k).

### 6.3 Что ограничивает качество

* **Нет loop closure.** Это LIO: курсовой дрейф не корректируется глобально.
  На 51 м он не проявился (гироскоп хороший, скан-матчинг держит курс), но на
  километровых трассах дрейф будет расти как 0.5–2 % пути — это следующий шаг.
* **Только point-to-line.** Нет point-to-plane (3D), нет интенсивности, нет
  семантики; динамические объекты (люди) попадут в карту.
* **Вырожденная геометрия.** В длинном коридоре продольное смещение не
  наблюдается (все нормали поперёк): фильтр честно увеличивает ковариацию, но
  специальной обработки вырожденности (solution remapping, как в LOAM/X-ICP) нет.
* **Кривизна.** Локально дуга столба радиусом 0.25 м на окне ±0.15 м даёт
  стрелку прогиба 4.5 см — это на пределе шума 2 см, поэтому такие точки не
  отбраковываются, а дают слегка повёрнутую нормаль. Дуги большого радиуса и
  углы обрабатываются правильно (углы отбрасываются, §тесты).

## 7. Тюнинг под Orange Pi Zero 3

* CPU governor на `performance` (`cpufrequtils`) либо `ondemand` с
  `up_threshold` ~40 — фильтр даёт редкие всплески, а не постоянную нагрузку.
* Драйвер колёс (`myrobot_driver`) и SLAM не конкурируют за ядро: у первого
  10 мс-таймер, у второго — событийный callback. При желании:
  `taskset -c 2 ros2 run ...` + `chrt -f 20`.
* `myrobot_wheel_fb` блокируется в `poll()` на sysfs — почти нулевой CPU, но
  при 1.6 кГц импульсов два узла дают заметный wakeup-rate; при проблемах с
  джиттером уменьшить частоту прерываний нельзя (аппаратно), зато можно
  поднять приоритет: `nice -n -18` (закомментировано в `description.launch.py`).
* Карта на 40×40 м при 0.05 м — 640k клеток OccupancyGrid (≈1.3 МБ на
  публикацию); при нехватке памяти уменьшить `map_max_extent`.
* `/dev/ttyS5` для лидара должен быть `chmod 0666` (см. `setup_gpio.sh`);
  UART5 на H618 не должен использоваться консолью.

## 8. Отладка без робота

Платформа (Orange Pi + лидар + IMU) не всегда доступна, поэтому в пакете есть
три независимых способа прогнать алгоритм:

### 8.1 Синтетические сенсоры (`fake_sensors.py`)

Самый лёгкий путь: узел подменяет железо и публикует ровно те же топики/фреймы,
что и робот, — `/scan` (720 лучей, `time_increment` на луч, шум 1 см, 2 %
выпадений), `/imu/data_raw` (100 Гц, гравитация, шум + постоянное смещение
гироскопа 0.002 рад/с), `/odom` + TF `odom -> base_link` с **ошибкой масштаба
колёс 2 %**, и `/ground_truth` с истинной позой. Экструзивные параметры берутся
из того же URDF, поэтому проверяется и они.

Луч и его поза считаются для **каждого луча отдельно** (свип 0.1 с), так что
компенсация искажений действительно проверяется, а не декларируется.

```
ros2 launch myrobot_custom_slam debug_fake.launch.py          # робот едет по кругу
ros2 launch myrobot_custom_slam debug_fake.launch.py drive:=static
ros2 launch myrobot_custom_slam debug_fake.launch.py odom_scale:=1.0
```

Симулятор не начинает движение, пока не увидит подписчика на `/scan`, и первые
5 с стоит на месте — иначе окно инициализации IMU заканчивается раньше, чем
узел вообще обнаружит топики.

### 8.2 Автоматическая проверка точности (`check_slam_accuracy.py`)

Сравнивает TF `map -> base_link` (вся цепочка SLAM: `map -> odom` от фильтра,
`odom -> base_link` от колёсной одометрии) с `/ground_truth` и печатает
среднюю/худшую/финальную ошибку; код возврата 1 при выходе за порог — годится
как CI-гейт.

```
ros2 run myrobot_custom_slam check_slam_accuracy.py --duration 30 --verbose
```

Замер на синтетике (30 с, круг R=1 м, 720 лучей, шум 1 см, выпадения 2 %,
ошибка одометрии 2 %, смещение гироскопа 0.002 рад/с):

```
samples=301 position error: mean=0.67 cm worst=1.34 cm final=0.74 cm
             yaw error:      mean=0.12 deg worst=0.29 deg
RESULT: PASS
```

То есть систематического дрейфа нет: ошибка не растёт за 30 с круга, а
`map -> odom` честно съедает ошибку масштаба одометрии.

### 8.3 Gazebo (полная физика)

`slam_gazebo.launch.py` поднимает `gzserver`, спавнит URDF (с плагинами
`gazebo_ros_diff_drive` / `ray_sensor` / `imu_sensor`), запускает
`robot_state_publisher`, скриптовый `circle_driver.py` и сам SLAM.

```
ros2 launch myrobot_custom_slam slam_gazebo.launch.py gui:=false rviz:=false
```

`gui:=false` — реально headless (запускается только `gzserver`, `gzclient` не
стартует), GPU не нужен. Мир по умолчанию — `worlds/room.world` (комната 8×8 м
плюс две колонны, асимметрично); пустой мир для лидара бессмысленен, регистрировать
нечего.

Чтобы это заработало, пришлось починить три вещи в модели (см. §9): кастеры,
`fdir1` колёс и порядок «инициализация → движение» (`circle_driver` ждёт
появления `/map`).

Проверено в контейнере (`./create_docker.sh gazebo`): IMU инициализируется
(`bg≈0.004`), робот проезжает круг, карта 2733 точки / 672 ячейки, `/map`
202×202 при 5 см (10×10 м — окно считается по данным, а не по максимуму),
0.3–0.4 мс на скан, RMS регистрации 0.4–0.5 см.

### 8.4 Dev-контейнер

`slam_gazebo` требует `ros-humble-gazebo-ros-pkgs`, которых нет в базовом
`desktop-full`. Докер-образ собирает всё нужное и монтирует воркспейс:

```bash
./create_docker.sh build      # образ myrobot_project:humble
./create_docker.sh sim        # синтетика + SLAM (headless)
./create_docker.sh check      # + отчёт по точности
./create_docker.sh gazebo     # Gazebo server + SLAM (headless)
./create_docker.sh shell      # интерактивно, с X11
```

Воркспейс монтируется, `entrypoint` сам сорсит ROS и, если нет `install/`,
собирает пакеты; `create_docker.sh rebuild` чистит артефакты и пересобирает.

## 9. Дефекты, найденные уже на синтетике (закрытый контур)

Прогоны `fake_sensors` + `slam_node` и Gazebo дали семь багов, которые
юнит-тесты поймать не могли:

1. **Heap overflow в публикации облака** (`slam_node.cpp`, `publishRegisteredScan`).
   Итераторы `PointCloud2Iterator` инкрементировались и на отброшенных точках,
   поэтому при `n_inliers < n_points` запись уезжала за конец буфера и процесс
   падал с `double free or corruption` на втором скане. Найдено прогоном под
   `-fsanitize=address` (ASAN указал точную строку). Теперь индексы inlier'ов
   собираются заранее, а итераторы двигаются только вместе с записью.
2. **Инициализация IMU на движущемся роботе.** Проверялось только
   `max|gyro| < 0.6 рад/с`, поэтому старт на ходу молча записывал скорость
   вращения робота в смещение гироскопа (`bg.z = 0.30` вместо `0.002` рад/с).
   Теперь проверяется ещё и разброс: `gyro std < 0.05`, `acc std < 0.5 м/с²`,
   а окно при отказе сбрасывается целиком (смешивать движущиеся и статичные
   сэмплы нельзя).
3. **Критерий покоя путал вибрацию с вращением.** Первая версия проверяла
   `max|gyro|` и разброс, поэтому вибрация платформы (std 0.07 рад/с) считалась
   движением, а медленное вращение с малым разбросом — покоем. Теперь решает
   **средний** модуль угловой скорости (`|gyro mean| < 0.05 рад/с`), а разброс
   лишь отсекает тряску; в тестах есть оба случая
   (`RejectsRotatingStartEvenIfSpreadIsLow`, `AcceptsVibratingPlatform`).
4. **Фрейм карты был повёрнут на 180°.** Фильтр живёт в системе IMU, а в URDF
   `imu_joint` имеет `rpy="0 0 -pi"`, поэтому карта оказывалась развёрнутой
   относительно базы робота (позиция ровно `-truth`, курсы отличались на 180°).
   Теперь начальная ориентация учитывает `base_to_imu` (карта = база в момент
   старта, как требует REP-105), а начало координат карты совпадает с **базой**,
   а не с IMU (смещение IMU `(-0.038, 0.024, -0.0185)` убрано) — это была
   оставшаяся систематическая ошибка 4 см.

5. **`fdir1="0 0 0"` у колёс** (в URDF ещё с master). Для ODE это невалидное
   направление трения: трения становились изотропными, база медленно
   доворачивалась и скользила при `cmd_vel = 0`. Исправлено на `1 0 0` с
   `mu1=0.5` (качение) / `mu2=1.0` (боковое).
6. **Двухколёсная база опрокидывалась в Gazebo** (обе опоры в `x=0`, центр масс
   выше). Добавлены два кастера-сферы с фиксированными джойнтами и малым
   трением — в симуляции поддерживают корпус, на реальном роботе инертны.
7. **Скриптовый драйвер начинал ехать до инициализации IMU**, и старт
   отбраковывался как «вращение». `circle_driver` теперь ждёт первый `/map`
   (то есть подтверждение, что фильтр инициализирован), и только потом едет;
   `fake_sensors` аналогично ждёт первого подписчика на `/scan`.
8. **Фильтр терял захват навсегда.** При шуме лидара 3 см и 10 % выпадений
   погрешность уходила в метры (38 см средняя, 176 см худшая): скан, где
   нашлось 31 соответствие из 646 (5 %), считался валидным (порог был
   абсолютный — 30 точек), фильтр уезжал, карта засорялась, и вернуться было
   нечем. Введены три гейта: **доля inlier'ов** (`min_inlier_ratio` 0.25),
   **физическая правдоподобность шага** (`max_translation_step` 0.5 м /
   `max_rotation_step` 0.5 рад за скан) и **перезапуск карты** после 15
   отброшенных сканов подряд (`reinit_after_rejected`) — карта
   переякоривается в текущей позе, иначе без loop closure восстановления нет
   вообще. Результат: тот же сценарий 5.95 см / 13.53 см вместо метров.
   Заодно узел теперь публикует `map -> odom` и при отброшенном скане —
   иначе у потребителей (nav2, RViz) робот просто исчезал.
9. **Порог качества линии путал шум с кривизной.** Критерий `λmin < 0.20·λmax`
   зависит только от отношения, а `λmin` растёт как σ²: при 3 см шума прямая
   стена даёт 0.12 и отбраковывалась (первые прогоны с жёстким 0.08 не
   работали вовсе), а пологая дуга проходила. Теперь гейт шумо-зависимый:
   `λmin ≤ max(ratio·λmax, (2σ)²)`.
10. **`myrobot_navigation2` ломал `colcon build --symlink-install`**: в
   `install(DIRECTORY launch map param rviz)` каталога `map/` нет. Обнаружено
   сборкой в контейнере (на хосте пакет просто не собирали). Теперь каталог
   добавляется в список только если существует.

## 10. Как запускать

```bash
# реальный робот: драйверы + описание + SLAM
ros2 launch myrobot_custom_slam slam.launch.py use_rviz:=true

# Gazebo (headless) / с GUI
ros2 launch myrobot_custom_slam slam_gazebo.launch.py gui:=false rviz:=false
ros2 launch myrobot_custom_slam slam_gazebo.launch.py

# синтетические сенсоры без Gazebo + проверка точности
ros2 launch myrobot_custom_slam debug_fake.launch.py
ros2 run myrobot_custom_slam check_slam_accuracy.py --duration 30

# только узел (если драйверы уже подняты)
ros2 run myrobot_custom_slam slam_node --ros-args \
  --params-file $(ros2 pkg prefix myrobot_custom_slam)/share/myrobot_custom_slam/config/slam.yaml

# бенчмарк ядра и тесты
ros2 run myrobot_custom_slam bench_slam 720 300
colcon test --packages-select myrobot_custom_slam
```

Первые ~1 с после старта — инициализация IMU (100 статических сэмплов): узел
оценивает смещения гироскопа/акселерометра и выравнивает платформу по вектору
гравитации. Робот в этот момент должен стоять; если детектор покоя не проходит
(вращение или вибрация), узел честно ждёт и повторяет, а не пишет скорость
робота в смещение гироскопа.

## 11. Ограничения и следующие шаги

* **Нет loop closure.** Это LIO, как и FAST-LIO2: дрейф по курсу накапливается
  (типично 0.5–2 % пути для 2D-лидара с IMU). Следующий шаг — позовый граф с
  ключевыми кадрами и поиском петель по дескрипторам скан-контекста
  (Scan Context / M2DP), затем глобальная оптимизация g2o/GTSAM.
* **Нет сохранения/загрузки карты.** Для повторной локализации нужен
  `serialize()/deserialize()` у `VoxelMap` + `map_server`-совместимый формат.
* **IMU-инициализация требует покоя.** Для «холодного» старта на ходу нужен
  статический детектор по скользящему окну (дисперсия акселерометра).
* **`ros2_mpu9250_driver`**: `frequency` в `mpu9250driver.cpp` считается как
  `1000ms / gyro_range`, то есть при `gyro_range: 0` узел делит на ноль/получает
  0 и частота публикации не та, что задана параметром `frequency`. Не правили,
  чтобы не менять поведение чужого пакета в этой ветке — при переходе на сырой
  IMU стоит исправить (`1000ms / frequency`).
